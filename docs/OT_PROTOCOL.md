# 本地不经意传输（OT）协议说明

本服务在**单个进程内**实现不经意传输（Oblivious Transfer），不依赖任何外部网络或第三方。
协议双方通过带完整性保护的内存通道交互，会话之间状态完全隔离。

- 发送方（Sender）持有若干组消息对 `(m0_i, m1_i)`。
- 接收方（Receiver）对每组持有一个选择位 `r_i ∈ {0,1}`，最终只能取回 `m_{r_i}_i`。
- 发送方无法获知任何选择位；接收方无法获知未被选择的另一条消息。

## 1. 总体结构

```
crypto/    群运算、随机源、对称原语、基础OT、IKNP原语
protocol/  错误码、消息类型、信封、二进制编解码、认证通道
session/   会话标识、生命周期状态机、并发注册表
transport/ 单进程内存定向队列
service/   SenderSession / ReceiverSession / OtService
config/    可配置项 OtProperties
```

一次运行中的两条逻辑方向各使用一个独立的有界阻塞队列：
`sender -> receiver` 与 `receiver -> sender`。队列容量可配置，协议消息严格成对交替，
因此即使消息数量很大，单条方向上的在途消息数也始终有界。

## 2. 1 选 2 基础传输（基于离散对数）

群参数采用 RFC 3526 的 2048 位 MODP 安全素数 `p = 2q+1`，在阶为 `q` 的二次剩余子群上工作，
生成元 `g = 4`。此外定义一个**离散对数未知**的固定元素 `U`（对固定种子做 SHA-256
后映射到 Z_p 再平方），作为公共参考串（CRS）。

协议采用 Chou–Orlandi 风格的 DH 构造：

1. 发送方选取 `a ← Z_q`，发送 `A = g^a`。
2. 接收方按选择位 `σ` 选取 `x ← Z_q`：
   - `σ=0`：发送 `B = g^x`；
   - `σ=1`：发送 `B = U·g^x`；
   并本地计算 `k = H(A^x)`。
3. 发送方计算两把密钥：
   - `k0 = H(B^a)`
   - `k1 = H((B/U)^a)`
4. 发送方用 `k0,k1` 分别经 AES-GCM 加密 `m0,m1`；接收方只能用其掌握的 `k` 解出一条。

`H` 是 HKDF-SHA256（域分隔标签 `dh-base-ot/v1`）。

- **接收方隐私（选择位隐私）**：`σ=0` 时 `B` 是随机子群元素，`σ=1` 时 `B=U·g^x`
  同样是随机子群元素，两种情况在 DDH 假设下对发送方不可区分。
- **发送方隐私**：未选中一侧的密钥是 `A` 在某个接收方无法构造的底数上的幂；
  要解出另一条消息，接收方必须求 `U`（或相关元素）的离散对数。
- 收到的群元素一律校验：范围、非平凡、且 `element^q = 1`（确属阶 `q` 子群）。
- 消息可以是任意字节串，两条消息长度不必相同，也允许长度为 0。

参数非法（消息对数 ≤ 0、消息对为 null、选择位越界等）会在会话进入 ACTIVE 之前直接抛出
`INVALID_PARAMETER` / `CHOICE_OUT_OF_RANGE`，不会建立可用会话。

## 3. 从少量基础传输扩展到大量随机传输（IKNP）

逐条执行基础 OT 需要大量公钥运算，代价不可接受。扩展阶段执行
`k = BASE_COUNT = 128` 次基础 OT，之后只用**对称密码原语**即可生成任意多条 OT。

### 3.1 角色反转

在扩展阶段角色互换：**最终消息接收方充当基础 OT 的发送方**，最终消息发送方充当
基础 OT 的接收方。

1. 最终消息发送方选取长度为 `k` 的随机比特串 `s`（IKNP 的关联差分 Δ = s）。
2. 对 `j = 0..k-1` 执行一次字符串 OT：
   - 基础 OT 发送方（= 最终消息接收方）准备两个长串 `(T_j, T_j ⊕ r)`，
     其中 `r` 是该批次长度为 `n` 的比特串，且对所有 `j` 使用**同一个** `r`；
   - 基础 OT 接收方（= 最终消息发送方）按选择位 `s_j` 只取得
     `T_j`（`s_j=0`）或 `T_j ⊕ r`（`s_j=1`）。
   这里字符串 `(T_j, T_j⊕r)` 先用基础 OT 协商出的对称密钥做 AES-GCM 密封，
   因此后续批次只复用同一批 128 个 DH 密钥，扩展本身不再做公钥运算。
3. 接收方的选择向量 `r` 编码进了这对串的相关性中：`T_j ⊕ (T_j⊕r) = r`。
   发送方只看到自己按 `s_j` 拿到的那一个串，不知道另一个，因而得不到 `r`。

### 3.2 行密钥（随机预言机）

双方把 `k` 个长度 `n` 的列转置成 `n` 个长度 `k` 的行：

- 最终消息发送方持有行 `Q_i`，其两把行密钥为
  - `K_i^0 = H(i, Q_i)`
  - `K_i^1 = H(i, Q_i ⊕ s)`
- 最终消息接收方持有行 `T_i`（= `Q_i` 或 `Q_i⊕s`，取决于其选择），
  其选中密钥为 `K_i^{r_i} = H(i, T_i)`。

可以验证：`r_i=0` 时 `T_i=Q_i`，得到 `K_i^0`；`r_i=1` 时 `T_i=Q_i⊕s`，得到 `K_i^1`。
`H` 为带 `(全局序号 i, side)` 域分隔的 HKDF-SHA256（标签 `iknp-ext-row/v1`），
作用是随机预言机，打破不同行之间共享同一差分 `s` 的关联性。

- **接收方隐私**：`r` 被 PRG 风格的随机串 `T_j` 一次性填充隐藏，发送方只持有
  相关对中的一个成员，求 `r` 等价于区分随机串。
- **发送方隐私**：接收方不知道 `s`（长度 128），除选中外无法得到另一条行密钥。
  随机预言机模型下其安全性不弱于逐条执行基础 OT。

真实消息只在**兑换**时才用行密钥经 AES-GCM 加密发送，未兑换的消息永远不会离开发送方。

### 3.3 仅使用对称原语

扩展阶段（含分批、行密钥、消息密封、消息完整性）只使用：

- HKDF-SHA256（密钥派生 / 随机预言机）
- AES-128/256-GCM（认证加密，128 位标签）
- HMAC-SHA256（信封完整性）

公钥运算仅出现在固定 128 次基础 OT 中，且其协商出的密钥被所有批次复用。

## 4. 选择位提交与消息兑换分离

扩展会话的使用顺序：

1. `createExtensionSession(n, batchSize)`：创建会话（尚未 ACTIVE）。
2. 接收方 `submitChoices(boolean[n])`：一次性提交**完整**选择向量，
   随后完成 128 次基础 OT 并准备好第一个扩展批次。
3. 接收方再按批次或单条兑换：
   - `redeemOne(i)`
   - `redeemRange(offset, length)`

兑换严格校验：

- 范围必须在 `[0, n)` 内，否则 `RANGE_OUT_OF_BOUNDS`。
- 必须从当前批次内尚未兑换的游标位置开始、连续、无间隙、不重叠；
  越界、错位、重复兑换一律 `REDEMPTION_CONFLICT` / `RANGE_OUT_OF_BOUNDS`。
- 必须按批次顺序兑换完当前批次，才能进入下一批。
- 兑换结果与提交的选择位严格一致。

## 5. 分批推进、有界内存与取消

- 批大小由配置项控制，最后一批自动吸收余量。
- 同一时刻只保留**当前批次**的列、相关行与行密钥；批次兑换完成即丢弃，
  因此单批内存占用有界（约为 `batchSize × 128 bit` 加消息缓冲），
  与总消息量无关。
- 接收方可随时 `cancel()`：向对端发送中止、关闭通道、清空当前批次与基础密钥、
  将会话标记为 ABORTED 并在注册表中保留墓碑。取消后不会留下任何能被后续会话
  观察到的中间状态，新会话使用全新随机 id 与密钥。

## 6. 并发、隔离与故障处理

- 每个会话拥有独立的状态对象、通道队列与 MAC 密钥，互不共享可变协议状态。
- 共享的注册表（`ConcurrentHashMap` + 原子状态引用）与 `SecureRandom`
  （本身线程安全）支持多会话并发。
- 每侧协议在独立工作线程运行；一侧抛异常会向对端发送带错误码的 ERROR/ABORT，
  对端接收时立即终止，选择位不会因此泄漏（选择位从不出现在任何消息中）。
- 一个会话的异常只影响自身，其他会话继续执行。
- 会话状态机：`PENDING -> ACTIVE -> COMPLETED`，任意非终态可进入 `ABORTED`；
  COMPLETED / ABORTED 为终态。中止或完成的会话 id 被墓碑化，永不重用。

## 7. 信封完整性与可区分错误码

每条协议消息封装为 `Envelope(sessionId, sequence, type, payload, tag)`：

- `sessionId`：128 位随机会话标识，防止跨会话混用。
- `sequence`：每个方向独立、严格递增的序号。
- `tag`：HMAC-SHA256，覆盖 `sessionId || sequence || type || payload`，
  收发两个方向使用**不同**的 MAC 密钥以防反射。

接收时依次校验：会话标识匹配、序号等于期望值（旧序号判重放、跳号判乱序）、
HMAC 恒定时间比较。载荷使用长度前缀编码，截断或尾随字节都会被拒绝。

可区分的失败原因由 `ErrorCode` 给出，例如：

| 错误码 | 含义 |
| --- | --- |
| `CROSS_SESSION_MESSAGE` | 消息绑定到了别的会话 |
| `MESSAGE_TAMPERED` | 完整性标签错误 / 群元素非法 / 认证失败 |
| `REPLAY_DETECTED` | 重复的序号 |
| `OUT_OF_ORDER` | 序号或批次乱序 |
| `TRUNCATED_MESSAGE` | 载荷截断或格式错误 |
| `RANGE_OUT_OF_BOUNDS` | 兑换范围越界 / 跨批次 |
| `REDEMPTION_CONFLICT` | 错位、有间隙或重复兑换 |
| `CHOICE_OUT_OF_RANGE` | 选择向量长度不匹配 |
| `INVALID_PARAMETER` | 非法入参，会话不建立 |
| `SESSION_ABORTED` / `CANCELLED` | 对端中止或主动取消 |
| `PROTOCOL_VIOLATION` | 消息类型/参数不符协议 |

## 8. 随机数来源

统一由 `crypto/CryptoRandom` 提供，底层为 `java.security.SecureRandom`：

- Linux：`NativePRNGNonBlocking`（内核 CSPRNG，非阻塞，线程安全）
- macOS：`NativePRNG`
- 其他平台：JVM 默认 `SecureRandom`

所有指数、选择串 `s`、`T_j`、`r`、nonce、会话 id 均来自该源；
不使用 `java.util.Random` 产生任何安全相关数据。

## 9. 配置项（`OtProperties`）

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `defaultBatchSize` | 8192 | 缺省每批扩展消息数 |
| `maxBatchSize` | 1,048,576 | 单批硬上限 |
| `queueCapacity` | 8 | 每个方向在途信封上限 |
| 批大小下限 | `BASE_COUNT = 128` | 小于 128 直接拒绝 |

可通过 `new OtService(new OtProperties(defaultBatchSize, maxBatchSize, queueCapacity), registry)`
自定义。批大小越大，单批吞吐越高但有界内存也越大。

## 10. 安全假设与边界

- 基础 OT 的安全性依赖于 MODP-2048 阶 `q` 子群上的 **DDH（离散对数）困难假设**。
- 扩展在**随机预言机模型**下达到半诚实（semi-honest）安全性；
  IKNP 本身针对半诚实参与方，不提供对主动恶意偏离输入编码的 UC/恶意安全。
  但所有传输消息都带认证，畸形、篡改、截断、重放、跨会话与中止都能被检测并终止。
- 128 位计算安全强度（`k=128`，AES/HMAC/SHA-256），DH 群为 2048 位。
